## 0. Словарик

| Термин | Простыми словами |
|---|---|
| **Контракт** | Общий файл с типами данных и интерфейсами. Все модули договорились говорить друг с другом только через него |
| **Заглушка (fake)** | Упрощённая реализация модуля. Нужна, чтобы соседний модуль можно было запустить и проверить, пока настоящий ещё пишется |
| **Ветка** | Параллельная версия кода в git. Каждое направление работает в своей ветке, в `main` сливаем после проверки |
| **CI** (continuous integration) | Автоматические проверки на GitHub при каждом пуше: линтеры, типы, тесты, сборка |
| **CD** (continuous delivery) | Автоматическая выкатка на сервер, если проверки CI зелёные |
| **Стенд** | Рабочая копия приложения в интернете: https://voice.planimetrika.online |
| **Docker / контейнер** | Приложение в «коробке» со всеми зависимостями. Запускается одинаково на ноутбуке и на сервере |
| **Docker Compose** | Файл, который описывает несколько контейнеров сразу (API, фронт, база, прокси) и связи между ними |
| **Обратный прокси** | Сервер на входе, который принимает запросы из интернета и раздаёт их внутренним сервисам (у нас nginx и Caddy) |
| **Смоук-тест** | Быстрая проверка «приложение вообще живое»: здоровье, вход, одна реплика, главная страница |
| **Eval / эталон** | Набор фраз с заранее вычисленными правильными ответами и скрипт, который считает метрики |
| **Оракул** | Правило, которое должно выполняться для **любой** фразы. Например, «в названии записи нет мусорных слов» |
| **xfail** | Тест, который «ожидаемо падает»: он описывает известную ошибку. Когда ошибку починят, тест неожиданно пройдёт (XPASS). Это и есть сигнал «починено» |
| **Rate limit** | Ограничение частоты запросов, например «не больше 20 реплик в минуту» |
| **CSP** | Заголовок, который говорит браузеру, откуда странице можно грузить скрипты, стили и куда подключаться. Защищает от внедрения чужого кода (XSS) |
| **HMAC** | Подпись данных секретным ключом. Без ключа подпись не подделать |

## 1. Как организована разработка

### 1.1. Направления: чаты 0–9

Работа поделена на **направления** (в документах они называются «чатами», потому что каждое вёл отдельный диалог с ИИ). У каждого направления свои ветки и свои папки. Источник — `docs/INTEGRATION.md`.

| Чат | Направление | Ветки | Папки (зона) |
|---|---|---|---|
| 0 | Каркас и интеграция | `main`, `infra/*` | `backend/app/contracts.py`, `container.py`, `api/`, `fakes/`, `docker-compose*.yml`, `Caddyfile`, `Makefile`, `.github/`, `deploy/`, `frontend/src/api/contracts.ts` |
| 1 | NLU и даты | `nlu/*` | `backend/app/nlu/` |
| 2 | Диалог | `dialog/*` | `backend/app/dialog/`, `backend/app/domain/` |
| 3 | Данные | `storage/*` | `backend/app/storage/`, `backend/app/cli.py`, `backend/eval/`, миграции |
| 4 | Голос | `voice/*` | `backend/app/voice/`, `backend/app/api/ws_voice.py`, `backend/Dockerfile` |
| 5 | Фронт | `web/*` | `frontend/` (кроме `src/api/contracts.ts`) |
| 6 | Продукт | `docs/*` | `README.md`, `docs/`, эталон вместе с чатом 3 |
| 7 | Тестирование | `qa/*` | `qa/`, `backend/tests/e2e/`, `backend/eval/asr/` |
| 8 | Безопасность | `sec/*` | `docs/security/`, `backend/tests/security/` |
| 9 | Каверзные реплики | `qa/adversarial-*` | `qa/adversarial/` |

Главные правила:

- **Чужие папки не трогаем.** Если направлению нужно исправление в чужой зоне, оно пишет готовый промпт владельцу: что сломано, где, как воспроизвести, по какому признаку считать «починено».
- **Чаты 7 и 8 находят, владельцы чинят.** Тестирование и безопасность сами чужой код не правят.
- **В `main` сливает только чат 0.** Это и есть роль интеграции, за которую ты отвечаешь на защите.

Как это соотносится с людьми: Артём — продукт и питч; Денис — интеграция, CI/CD, безопасность, слепой тест; Алексей — NLU и LLM; Александр Щенников — голос и диалог; Арсений — данные, поиск, метрики; Александр Матвеев — интерфейс (таблица «Команда» в `README.md`).

### 1.2. Единый контракт

Файл `backend/app/contracts.py` — общий язык всех модулей. В нём:

- типы данных на Pydantic: `Item` (запись), `TimeSpec` (разобранное время), `Slots` (поля команды), `Command`, `DialogState`, `AssistantReply`, `ActionRecord`;
- перечисления `ItemType`, `ItemStatus`, `Intent` (`create_item`, `list_items`, `search_items`, `update_item`, `complete_item`, `delete_item`, `undo`, `confirm`, `reject`, `smalltalk`, `unknown`);
- интерфейсы (Python `Protocol`): `DateResolver`, `NLU`, `ItemRepository`, `SearchEngine`, `STTProvider`, `TTSProvider`, `Orchestrator`.

В коде `CONTRACT_VERSION = "1.2"`. История изменений — `docs/CONTRACT.md`:

| Версия | Дата | Что изменилось |
|---|---|---|
| 1.1 | 21.10 | `Item.id = 0` (id выдаёт хранилище), `TimeSpec.has_date`, журнал действий `ActionRecord` для «Отменить», интервалы `[start, end)`, заголовок `X-Freeze-Now` для тестов (в prod запрещён) |
| 1.2 | 21.10, 23:40 | `DialogState.last_command` — для «а на следующей неделе?» и «нет, в 11»; `POST /api/undo` сбрасывает открытое уточнение |
| API 1.3 | 23.10 | Вход через сессию: `POST/GET/DELETE /api/session`, cookie `pomnyu_session`, 429 с `Retry-After`, состояние диалога по паре (пользователь, сессия). Сам `contracts.py` не менялся |

Порядок изменения контракта: направление просит → просьба идёт в чат 0 → чат 0 меняет `contracts.py`, `frontend/src/api/contracts.ts`, заглушки и `docs/INTEGRATION.md` → всем рассылается сводка. Фронт проверяет, что его копия контракта совпадает с бэкендом, командой `npm run check:contract`.

### 1.3. Заглушки и подмена через `container.py`

В `backend/app/fakes/` лежат простые реализации всех интерфейсов: `dates.py`, `nlu.py`, `orchestrator.py`, `repository.py` (хранилище в памяти, умеет грузить CSV), `search.py`, `voice.py`.

`backend/app/container.py` собирает приложение. Функция `build_container(settings)` смотрит на переменные окружения и для каждого слота выбирает заглушку или настоящий модуль:

| Переменная | Что подключает |
|---|---|
| `NLU_IMPL=real` | `app.nlu.build_date_resolver`, `app.nlu.build_nlu` |
| `STORAGE_IMPL=postgres` | `app.storage.build_repository`, `app.storage.build_search` |
| `STT_PROVIDER≠fake`, `TTS_PROVIDER≠fake` | `app.voice.build_stt`, `app.voice.build_tts` |
| `DIALOG_IMPL=real` | `app.dialog.build_orchestrator(...)` |

Настоящие модули импортируются **лениво** (через `importlib`), только когда включены. Если фабрики нет, приложение падает с понятным сообщением «Реальная реализация не найдена… Верните заглушку в .env».

**Зачем это было нужно.** В первый день не было ни NLU, ни базы, ни голоса. Благодаря заглушкам каждое направление сразу могло запускать приложение целиком и проверять свой модуль поверх чужих заглушек. Например, настоящий NLU поверх заглушки диалога. Так шесть человек работали параллельно и не ждали друг друга.

В том же файле: `SessionStore` — состояние диалога в памяти по ключу (пользователь, сессия), не больше 10 000 сессий, срок жизни 24 часа (защита SEC-01 и SEC-11), и `limiter` — счётчик для лимитов частоты.

### 1.4. Ветки и слияние

- Ветки версий: `nlu/v1…v6`, `dialog/v1…v6`, `storage/v1…v3`, `voice/v1…v4`, `web/v1…v4`, `docs/v1…v2`, `qa/v1…v4`, `qa/adversarial-v1…v2`, `sec/v1…v3`. Каждая новая версия — новая ветка, старые не переписываются, поэтому историю легко восстановить.
- Слияние в `main` — только через интеграцию (чат 0) и только с `git merge --no-ff`, чтобы в истории было видно, какая ветка когда вошла.
- Пока у команды не было доступа к GitHub, обмен шёл архивами; их раскладывал по веткам `deploy/merge_incoming.sh`.
- Чек-лист перед слиянием (`docs/INTEGRATION.md`): `make check` зелёный; чужие папки не тронуты; новые зависимости — в `backend/pyproject.toml` или `frontend/package.json`; новые переменные — в `.env.example` и README; сводка «что сделано, что изменилось в интерфейсах».
- Шаблон PR — `.github/pull_request_template.md`: направление, изменения контракта, `make check`, метрики `make eval` до и после.
- Ветки `dependabot/...` создаёт робот обновлений (см. 2.4). Их сливают только после зелёного CI и просмотра.

## 2. CI/CD: что проверяется автоматически

Файлы — `.github/workflows/`. Три workflow и настройки Dependabot.

### 2.1. `ci.yml` — проверки на каждый пуш

Запускается на пуш в `main` и на каждый pull request. `concurrency` с `cancel-in-progress` отменяет старый прогон, если в ту же ветку пришёл новый коммит.

**Джоб `backend`** (Ubuntu + сервис PostgreSQL `pgvector/pgvector:pg16`):

| Шаг | Что проверяет | Зачем |
|---|---|---|
| Python 3.12, кэш pip | — | одинаковая версия с Docker-образом |
| `ffmpeg` | — | нужен голосовым тестам (декодирование аудио) |
| `ruff check` + `ruff format --check` | стиль и типовые ошибки (неиспользуемые импорты, опасные конструкции) | код шести человек и ИИ выглядит одинаково, мелкие баги ловятся до запуска |
| `mypy app` | статическая проверка типов | ловит несовпадение с контрактом: передали не тот тип — CI красный |
| migrate + seed | расширения `vector`, `pg_trgm`, миграции Alembic, импорт CSV в пользователя 1 | тесты идут на настоящей базе, как на стенде |
| `pytest -q -rs` | все тесты, включая PostgreSQL, голос и безопасность | регрессия: старое не сломалось; `-rs` показывает причины пропусков |
| eval (настоящие модули) | эталонный набор, `--min-recall 0.9`, отчёт — в Summary прогона | качество понимания не просело; таблица видна прямо на GitHub |

**Джоб `frontend`**: Node 22, `npm ci`, `npm run build` (внутри `tsc -b` — проверка типов TypeScript и сборка Vite).

**Джоб `docker`** (только после зелёных backend и frontend): `docker compose config -q` для обычного и prod-режима — файлы compose синтаксически верны; `VOICE_MODELS=0 docker compose build api web` — образы собираются (без весов моделей, чтобы не качать гигабайты).

**Джоб `security`** (SEC-12). Пока стоит `continue-on-error: true`: находки видны, но джоб не блокирует слияние, потому что сначала их нужно разобрать.

| Шаг | Что ищет |
|---|---|
| `gitleaks git --log-opts=--all` | секреты (ключи, пароли, токены) во **всей истории** всех веток, с маскировкой в выводе |
| `pip-audit` | Python-зависимости с известными уязвимостями (CVE) |
| `npm audit --omit=dev` | то же для зависимостей фронта, попадающих в продакшн |

### 2.2. `adversarial.yml` — каверзные реплики

- Запуск: пуш в `main`, если менялись `backend/app/**`, `backend/eval/**`, `qa/adversarial/**`; по расписанию `17 3 * * *` (UTC) = **06:17 МСК**, чтобы утренняя сводка видела свежий результат; вручную.
- Отдельно от CI, потому что идёт около 10 минут и не должен задерживать деплой. Не блокирует: это «градусник», а не шлагбаум.
- Окружение: PostgreSQL, `NLU_IMPL=real`, `DIALOG_IMPL=real`, `STORAGE_IMPL=postgres`, `LLM_PROVIDER=rules` (без LLM). Поэтому результат — **нижняя граница**: на стенде GigaChat дополнительно подстраховывает.
- Результат: `adv_report.md` в Summary и артефакт `adversarial` (`adv_report.md`, `adv_rows.json`), хранится 14 дней.

### 2.3. `deploy.yml` — автодеплой

```
пуш в main → CI зелёный → Deploy → SSH на сервер → деплой → смоук стенда
```

| Деталь | Что это и зачем |
|---|---|
| `on: workflow_run` CI, ветка `main`, `completed` + условие `conclusion == 'success'` | деплой только после **зелёного** CI в `main`. Красный CI — на стенд ничего не уходит |
| `workflow_dispatch` | ручной запуск: Actions → Deploy → Run workflow |
| `concurrency: deploy`, `cancel-in-progress: false` | два деплоя не идут одновременно, второй ждёт первого |
| `environment: production` | секреты сервера лежат в окружении GitHub «production», а не на уровне репозитория. В его настройках можно включить ручное подтверждение и разрешить только `main` (SEC-04) |
| Check secrets | если `VPS_HOST` не задан (например, в форке), деплой пропускается, а не падает |
| `appleboy/ssh-action@7eaf7667…` (v1.2.0) | действие закреплено по **полному SHA коммита**, а не по тегу. Тег можно перевесить на вредный код, SHA — нельзя (SEC-12) |
| `fingerprint: secrets.VPS_FINGERPRINT` | отпечаток ключа сервера. Защита от подмены сервера: если ответит чужая машина, подключение оборвётся |
| `script` | если на сервере есть `/usr/local/sbin/gorky-deploy` — `sudo -n` его; иначе старый путь `make shared-up` |
| Smoke test | после деплоя `./deploy/smoke.sh` против `DEPLOY_URL`. Красный смоук = красный деплой, сразу видно |

**Forced command.** После `deploy/harden-deploy-user.sh` ключ GitHub лежит у пользователя `deploy` с пометкой `restrict,command="sudo -n /usr/local/sbin/gorky-deploy"`. Это значит: что бы ни прислал клиент, сервер выполнит **только** скрипт деплоя. Поле `script` в workflow при этом игнорируется. Подробно — раздел 3.6.

Названия секретов (значения не печатаем никогда): `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_FINGERPRINT`, `DEPLOY_URL`.

### 2.4. `dependabot.yml`

Робот GitHub раз в неделю проверяет обновления и открывает PR: pip (`/backend`, до 5 PR), npm (`/frontend`, до 5), GitHub Actions, Docker-образы `backend` и `frontend`. Сейчас в репозитории есть его ветки (например, обновления `actions/checkout`, `appleboy/ssh-action`, базового образа nginx фронта). Правило: сливать только после зелёного CI; обновление `ssh-action` меняет SHA, его проверяем особенно внимательно. До защиты крупные обновления лучше не сливать — см. заморозку кода.

## 3. Стенд

### 3.1. Путь запроса

```
Браузер
  │ HTTPS :443
  ▼
nginx на хосте  (сертификат Let's Encrypt через certbot, лимиты по IP, WebSocket)
  │ http://127.0.0.1:8080
  ▼
Caddy в контейнере  (заголовки безопасности, CSP, маршрутизация)
  ├── /api/*  /ws/*  /calendar/*  /health  /docs  /openapi.json  →  api:8000  (FastAPI, uvicorn)
  └── всё остальное                                              →  web:80    (nginx со сборкой React)
                                                                       │
                                                         api ──▶ db:5432 (PostgreSQL 16 + pgvector)
```

Почему два прокси. Сервер общий с другим приложением владельца, и порты 80/443 уже заняты его nginx. Поэтому наш стек работает «соседом»: слушает только локальный адрес `127.0.0.1:8080`, а HTTPS и лимиты по IP делает существующий nginx. Caddy внутри стека отвечает за маршруты и заголовки, одинаково локально и на сервере.

### 3.2. Файлы Docker Compose

Файлы складываются слоями: базовый + один дополнительный.

| Файл | Когда используется | Что добавляет |
|---|---|---|
| `docker-compose.yml` | всегда | 4 сервиса: `db` (pgvector:pg16, healthcheck `pg_isready`, том `pgdata`, расширения из `deploy/initdb`), `api` (сборка `backend/`, `.env`, `DATABASE_URL`, `SEED_CSV`, `./data` только для чтения, ждёт здоровую db), `web` (сборка `frontend/`), `caddy` (`caddy:2-alpine`, ждёт здоровый api) |
| `docker-compose.override.yml` | подхватывается **сам** при `docker compose up` без `-f` — локальная разработка | Caddy на `127.0.0.1:8080`, база на `127.0.0.1:5432` — только локально, не наружу (SEC-06) |
| `docker-compose.prod.yml` | `make prod-up` — отдельный сервер | `APP_ENV=prod`, Caddy сам получает сертификат на `DOMAIN`, порты 80/443 |
| `docker-compose.shared.yml` | `make shared-up` — **наш стенд** | `APP_ENV=prod`, обязательный `SESSION_SECRET`, Caddy только на `127.0.0.1:8080`, лимиты ресурсов и защита контейнеров |

Что задаёт `docker-compose.shared.yml` (SEC-05):

| Сервис | Память | CPU | Процессов | Ещё |
|---|---|---|---|---|
| api | `API_MEM_LIMIT`, по умолчанию 2500m (модели голоса 1,1–2 ГБ) | 1.5 | 256 | `cap_drop: [ALL]`, `no-new-privileges` |
| db | 512m | 0.5 | 256 | `no-new-privileges` |
| web | 128m | 0.5 | 256 | `no-new-privileges` |
| caddy | 128m | 0.5 | 256 | `no-new-privileges` |

- **Лимиты памяти и CPU** — наш стек не может «задушить» соседнее приложение на том же сервере.
- **`pids_limit: 256`** — защита от «форк-бомбы»: процесс не наплодит тысячи процессов.
- **`cap_drop: [ALL]`** — у контейнера API отобраны все особые права ядра Linux.
- **`no-new-privileges`** — процесс внутри не может повысить свои права (например, через setuid-программу).
- **Ротация логов** (`json-file`, `max-size: 10m`, `max-file: 3`) — не больше ~30 МБ логов на сервис, диск общего сервера не переполнится.
- **`SESSION_SECRET: ${SESSION_SECRET:?…}`** — без секрета compose не стартует, и **старая версия продолжает работать**. Безопасный отказ.

### 3.3. `Caddyfile`

- Глобально: `trusted_proxies static private_ranges` (SEC-17) — заголовку `X-Forwarded-For` верим, только если он пришёл от прокси из частной сети (nginx на хосте, сеть Docker). Иначе клиент мог бы подставить чужой IP и обойти лимит входа.
- Сайт `{$SITE_ADDRESS::8080}`: сжатие `zstd gzip`; маршрут `@backend` → `api:8000`, всё остальное → `web:80`.
- Заголовки безопасности:

| Заголовок | Зачем |
|---|---|
| `Strict-Transport-Security` | браузер год ходит только по HTTPS |
| `X-Content-Type-Options nosniff` | браузер не «угадывает» тип файла (защита от подмены JSON на скрипт) |
| `Referrer-Policy strict-origin-when-cross-origin` | чужим сайтам не уходит полный адрес страницы |
| `Permissions-Policy "microphone=(self)"` | микрофон доступен только нашей странице, не встроенным чужим |
| `Content-Security-Policy` | скрипты, шрифты, стили — только со своего домена; WebSocket — только `wss://{host}` (свой хост); `frame-ancestors 'none'` — нас нельзя встроить во фрейм; `object-src 'none'` (SEC-09) |
| `X-Frame-Options DENY` | то же против встраивания, для старых браузеров |
| `-Server` | не раскрываем, какой сервер стоит |

### 3.4. `deploy/shared/nginx-voice.conf` — nginx на хосте

Файл ставится в `/etc/nginx/sites-available/voice.conf`, сертификат выпускает `certbot --nginx -d <домен>` (он же дописывает блок для 443).

| Настройка | Что делает |
|---|---|
| `limit_req_zone … zone=voice_req … rate=5r/s` | общий лимит: 5 запросов в секунду с одного IP |
| `limit_req_zone … zone=voice_chat … rate=30r/m` | реплики `/api/chat` и `/api/undo`: 30 в минуту с IP, не зависит от cookie |
| `limit_conn_zone … zone=voice_conn` | счётчик одновременных соединений |
| `client_max_body_size 20m` | предел размера тела запроса (аудио) |
| `location /ws/` | `limit_conn voice_conn 10` (не больше 10 WebSocket с IP), заголовки `Upgrade`/`Connection "upgrade"` для WebSocket, таймаут 300 с |
| `location ~ ^/api/(chat\|undo)$` | обе зоны: `voice_chat burst=10` и `voice_req burst=20`, ответ 429 |
| `location /` | `voice_req burst=20`, 429, тоже с поддержкой WebSocket |
| `X-Real-IP $remote_addr`, `X-Forwarded-For $proxy_add_x_forwarded_for` | передаём настоящий IP клиента дальше; nginx **перезаписывает** `X-Real-IP`, поэтому клиент его не подделает |

Зоны `limit_req_zone` объявлены в файле нашего сайта и **соседнее приложение не затрагивают**. Почему лимит по IP именно в nginx: за Caddy все клиенты приходят к API с одного адреса шлюза Docker, а nginx видит настоящий адрес.

Если на хосте Caddy, а не nginx, — используется `deploy/shared/Caddyfile.snippet`. Посмотреть, что уже стоит на сервере, — `deploy/shared/diagnose.sh` (ОС, память, занятые порты, веб-серверы, certbot).

### 3.5. Образ API: `backend/Dockerfile` и `docker-entrypoint.sh`

Сборка в три стадии:

1. **deps** — Python-зависимости. При `VOICE_MODELS=1` ставится CPU-версия torch (≈200 МБ вместо ≈2,5 ГБ с CUDA) и GigaAM.
2. **models** — веса моделей отдельным слоем (кэшируется). При `GIGAAM_QUANTIZE=int8` модель квантуется прямо при сборке.
3. **runtime** — итоговый образ: `ffmpeg`, `curl`, системный пользователь `app` (uid 10001), веса копируются сразу с владельцем `--chown` (иначе гигабайт весов продублировался бы отдельным слоем).

Важные строки:

- `USER app` — процесс **не root** (SEC-05). Пишет только в `/app/.tts-cache`, `/models`, `$HOME/.cache`, `/dev/shm`.
- `HEALTHCHECK` — каждые 15 с `curl http://localhost:8000/health`, `start-period=60s` (модели грузятся при старте). Caddy стартует, только когда API здоров.
- `uvicorn … --workers 1` — строго один процесс: модели живут в памяти процесса, второй процесс удвоил бы RAM. Параллельность — через asyncio. Поэтому лимиты частоты считаются в памяти, без Redis.
- `--proxy-headers --forwarded-allow-ips=<только частные сети и localhost>` — uvicorn берёт IP клиента из `X-Forwarded-For`, но доверяет только прокси из частных сетей (SEC-17). Раньше стояло `*` — тогда IP подделывался.
- `--ws-max-size 4194304` — WebSocket-сообщение не больше 4 МБ.
- `MALLOC_ARENA_MAX=2` — меньше пустого роста памяти.

`docker-entrypoint.sh` при `STORAGE_IMPL=postgres` перед стартом:

1. `alembic … upgrade head` — миграции базы.
2. Импорт CSV организаторов в пользователя 1 (`python -m app.cli import-csv`). Импорт **идемпотентный**: повторный запуск пропускает уже существующие записи, поэтому перезапуск контейнера данные не дублирует.
3. Ошибка импорта **не роняет API**, но громко пишется в лог (`seed: ОШИБКА…`), а `/health` покажет `seed_items: 0` — это ловит смоук.
4. `exec "$@"` — запуск uvicorn.

### 3.6. Скрипты деплоя на сервере

**`deploy/remote-deploy.sh`** — ставится как `/usr/local/sbin/gorky-deploy` (владелец root, 0755). Это единственное, что может сделать ключ GitHub Actions:

1. `flock` на `/run/gorky-deploy.lock` — если деплой уже идёт, второй тихо выходит (SEC-19: два параллельных `up --build` нагрузили бы общий сервер и устроили гонку).
2. `git fetch origin main` + `git reset --hard origin/main` — код на сервере всегда ровно как в `main`.
3. `docker compose -f docker-compose.yml -f docker-compose.shared.yml up -d --build --remove-orphans`.
4. `docker image prune -f` — удалить старые образы, чтобы не забивать диск.
5. Аргументы и присланная по SSH команда игнорируются.

**`deploy/harden-deploy-user.sh`** (SEC-04, SEC-15) — переводит автодеплой с root на пользователя `deploy`. Запускается под root, **с открытой второй root-сессией** на случай ошибки.

| Шаг | Что делает |
|---|---|
| 0. Проверки | запускать от root; файл публичного ключа Actions — ровно одна строка; тип ключа известен; `ssh-keygen` его принимает. Любое сомнение — остановка **до** изменений |
| 1. Пользователь | создаёт `deploy` без пароля, **убирает его из группы docker** (группа docker = фактически root), ставит `gorky-deploy`, пишет sudoers `deploy ALL=(root) NOPASSWD: /usr/local/sbin/gorky-deploy ""` — пустые кавычки запрещают аргументы. Файл сначала проверяется `visudo -cf`, потом устанавливается (битый sudoers сломал бы sudo всем) |

| Итог | печатает, что поменять в GitHub: `VPS_USER=deploy` и `VPS_FINGERPRINT` |

Скрипт проверен в песочнице с настоящими `adduser`, `visudo`, `sshd`: с ключом deploy любая команда (`id`, `cat /etc/shadow`, `bash`) выполняет только деплой, проброс портов отклоняется (`docs/security/REPORT.md`, раздел SEC-15). Повторный запуск безопасен (идемпотентен).

1. До 30 попыток с паузой 3 с ждёт `/health`.
2. Проверяет `"db":"ok"` и что `seed_items` не 0 (иначе «база пуста — CSV не загрузился»).

### 4.2. Как работает вход (`backend/app/api/session.py`)

- `POST /api/session {"user_id": 1|2|3}` — разрешены только id из `DEMO_USERS` (по умолчанию 1, 2, 3). Вход ограничен: 10 в минуту на IP (`rate_login_per_min`).
- Сервер выдаёт cookie: `base64url(json{uid, sid, exp}) + "." + base64url(HMAC-SHA256(SESSION_SECRET, payload))`. Без секрета подпись не подделать.
- Флаги cookie: `HttpOnly` (JavaScript страницы её не прочитает — XSS не украдёт), `Secure` (только по HTTPS), `SameSite=Strict` (чужой сайт не отправит её от имени пользователя), срок 24 часа.
- `verify_cookie()` проверяет подпись через `hmac.compare_digest` (сравнение без утечки по времени), срок и что пользователь из списка. Её же использует WebSocket.
- `GET /api/session` — кто я (или 401), `DELETE` — выход.
- Почему не JWT-библиотека: подпись из стандартной библиотеки — 30 строк и ноль зависимостей при той же защите для одного сервиса.

`backend/app/api/deps.py`, `get_user_id`: сначала cookie; если её нет и `APP_ENV=prod` без `ALLOW_HEADER_AUTH` — 401; вне prod — заголовок `X-User-Id` (для тестов и eval), иначе 1. `get_cookie_session` отдаёт `sid` из cookie как ключ лимитов.

**`ALLOW_HEADER_AUTH`** — переходный режим: в prod временно принимать `X-User-Id`, пока фронт не перешёл на cookie. По умолчанию `false`. На стенде его нужно выключить до защиты (раздел 7).

### 4.3. Лимиты частоты

`api/ratelimit.py` — «скользящее окно» в памяти: для каждого ключа хранятся времена запросов; если за окно их больше лимита — 429 и `Retry-After`. Один процесс uvicorn → Redis не нужен.

Значения в `backend/app/config.py`:

| Настройка | По умолчанию | Ключ |
|---|---|---|
| `rate_chat_per_min` | 20 в минуту | `/api/chat`, `/api/undo` на (пользователь, `sid` из cookie) |
| `rate_service_per_hour` | 3000 в час | на весь сервис; общий бюджет и для голосовых реплик |
| `rate_tts_per_min` | 30 в минуту | `/api/tts` на пользователя |
| `rate_login_per_min` | 10 в минуту | `POST /api/session` на IP |

WebSocket (`ws_voice.py`): лимит сокетов на процесс и на сессию (close 1013), закрытие после 60 с тишины (4408), лимит реплик в минуту на сессию из cookie, распознавание под общим семафором; если очередь занята — «Сервер занят, повторите через пару секунд». Поверх всего — nginx по IP (раздел 3.4).

### 4.4. Prod-проверки при старте (`config.py`, `_prod_guards`)

При `APP_ENV=prod` приложение **отказывается стартовать**, если:

- `SESSION_SECRET` короче 32 символов;
- при PostgreSQL пароль в `DATABASE_URL` пустой или `app`, `postgres`, `password`;
- есть ICS-токен короче 22 символов (кроме демо-токена `demo` пользователя 1).

Смысл: небезопасную конфигурацию нельзя выкатить «случайно». Вместе с `${SESSION_SECRET:?…}` в compose это даёт безопасный отказ: старая версия продолжает работать. Ещё в prod запрещён тестовый заголовок `X-Freeze-Now` (подмена «сейчас»): ответ 400.

### 4.5. Что ещё проверено и чисто

Из раздела «Проверено — уязвимостей нет» отчёта: SQL-инъекции (только ORM с параметрами); prompt injection (в схеме функций LLM нет ни `user_id`, ни `item_id`, удаление — одна запись и только после «да»); XSS (React выводит текст, `innerHTML` нет); секреты в git (gitleaks по всем веткам); зависимости (0 известных уязвимостей на 22.10); порты (в prod/shared наружу только то, что нужно).

## 5. Система качества: четыре уровня

Идея: эталонный набор составили мы сами, поэтому своя система проходит его слишком легко. Каждый следующий уровень — фразы, которые всё дальше от разработчиков.

```
1. Эталон (100 фраз, наши)          → 100%
2. Каверзные реплики (583, спец.)   → 50% → 92%, свежие 25/30
3. Живые логи стенда (реальные)     → тесты qa/live, known = xfail
4. Слепой тест (люди, не видели код) → 26–27.10
```

Команды (`README.md`, раздел «Качество»): `make test` (≈1300 тестов), `make eval-real`, `make adversarial`.

### 5.1. Уровень 1 — эталонный набор

- Файл `backend/eval/golden_eval.jsonl` — 100 запросов. Ожидаемые ответы **вычислены скриптом по CSV организаторов**, а не написаны руками.
- Состав: 14 фраз из ТЗ дословно, 10 перефразировок, 11 с ошибками распознавания и опечатками, 8 граничных дат и времени, 10 многоходовых диалогов, 29 поисковых.
- Прогон `backend/eval/run_eval.py`: каждая строка — в чистой среде (свежая копия данных пользователя), `history` проигрывается в той же сессии, «сейчас» зафиксировано (21.10.2026 14:00 МСК), даты сравниваются с точностью до минуты.
- Результат (`backend/eval/report.md`, без LLM, PostgreSQL): **100/100** сценариев, интент 100%, даты 100%, Recall@5 поиска 100%, MRR 0,98, задержка текста p50/p95 — 0,01/0,04 с.

### 5.2. Уровень 2 — каверзные реплики

- Набор — `qa/adversarial/*.jsonl` (собирает `build.py` из `scenarios/*.py`, руками не правим), 583 сценария: 5 задач пользователя (записать дело, записать встречу, узнать, что впереди, найти старое, поправить) × оси: порядок слов, разговорное время, обрезки распознавания, числа словами, паразиты и мат, самопоправки, две команды, контекст, прошлое/будущее, вежливые формы, бессмыслица, реальные фразы со стенда.
- Прогон — `backend/eval/run_adversarial.py`. Две группы проверок:
  - `expect` — то, что автор сценария записал как однозначное (intent, action, дата, время, тип, слова в названии…);
  - **оракулы** — правила для любой фразы: O1 — в названии нет мусора (пустое, местоимения, слова времени, мат); O2 — ответ называет сохранённое время; O3 — «прошлое» не возвращает будущие записи; плюс нет исключений сервера.
- Где ожидание спорное (ТЗ молчит), допускаются оба исхода или время не проверяется.
- Динамика (`qa/adversarial/BASELINE.md`, только правила, без LLM):

| | 24.10, 00:40 | 24.10, 03:50 |
|---|---:|---:|
| Целиком | 50% (282/569) | **92% (535/583)** |
| Записать дело | 58% | 83% |
| Записать встречу | 41% | 97% |
| Узнать, что впереди | 40% | 98% |
| Найти старое | 71% | 87% |
| Поправить | 38% | 94% |

- **Проверка на подгонку:** 30 новых фраз, которых не видел ни один разработчик, — **25/30**. А на 530 сценариях с неизменными ожиданиями рост 52% → 90%: это настоящее улучшение, а не смягчение ожиданий.
- Где запускается: workflow Adversarial (пуш и 06:17 МСК) и ежедневная проверка.

### 5.3. Уровень 3 — живые наборы из логов

- Реплики стенда раз в час уходят в приватный `gorky_logs` (раздел 3.6).
- Неудачные фразы становятся строками `qa/live/ГГГГ-ММ-ДД.jsonl` (сейчас 22.10 — 33 строки, 23.10 — 57). Черновик из лога делает `qa/tools/import_turn_log.py`.
- Строка: `id`, класс ошибки (`A` распознавание, `B` понимание, `C` диалог/ответ, `D` запись/фронт, `OK`), владелец, номер находки, текст, история, «сейчас», `expect` (intent, action, время, слова в названии, «записи не изменились» и т.д.).
- Тест — `backend/tests/e2e/test_live.py`: каждая строка — отдельный тест в свежем приложении (настоящие NLU и диалог, CSV, «сейчас» = момент реплики).
- **`known: true` → `xfail`.** Находка ещё не исправлена, тест ожидаемо падает и не роняет CI. Когда владелец починит, тест станет XPASS — это и есть **критерий «починено»**. `qa/regress.py` подсвечивает такие случаи, чат 7 снимает `known`. Сейчас `known` — 11 строк (все в наборе 23.10).
- `known_on: ["memory"]` — падает только на хранилище в памяти, а на PostgreSQL (как на стенде) обязано проходить.

### 5.4. Уровень 4 — слепой тест

Материалы — в ветке `origin/qa/v4`, папка `qa/blind/`. Смотреть, не переключая ветку: `git show origin/qa/v4:qa/blind/host_sheet.md` (то же для `README.md`, `cards.md`, `reset_user3.sh`, `summarize.py`).

После теста: перенести таблицы в `qa/blind/results/2026-10-26.csv` и `…-27.csv` по `results_template.csv`, запустить `python qa/blind/summarize.py qa/blind/results/*.csv` → доля ✓, «✓ с первой фразы», медианы секунд и попыток по задачам ТЗ и устройствам. ## 6. Выкатка, откат, авария

### 6.1. Исправление от коммита до стенда

1. Владелец зоны делает ветку новой версии (`nlu/v7` и т.п.), коммитит, локально `make check`.
2. Интеграция (ты или ежедневная проверка) сливает в `main` через `git merge --no-ff`, снова `make check`.
3. `git push origin main` → **CI** (backend, frontend, docker, security), ≈ несколько минут.
4. CI зелёный → **Deploy** сам: SSH → `gorky-deploy` → `git reset --hard origin/main` → `docker compose … up -d --build`.
5. **Smoke test** в том же workflow. Зелёный — исправление на стенде.
6. Проверить вручную: `curl https://voice.planimetrika.online/health`, одна фраза на сайте.
7. Если исправление закрывало живую находку — тест в `qa/live` стал XPASS, снять `known`.

Статус прогонов: вкладка Actions или `gh run list -R riikinkukko/gorky_code -L 4`.

### 6.2. Откат

Сервер всегда приводит код к `origin/main` (`reset --hard`), поэтому **правильный откат — через `main`**:

```bash
git revert <плохой-коммит>      # или: git revert -m 1 <коммит-слияния>
git push origin main             # CI → Deploy → смоук сами
```

- `revert` не переписывает историю, а добавляет обратный коммит — безопасно для всех.
- Повторить деплой без нового коммита: Actions → Deploy → Run workflow.
- Аварийно на сервере (нужен доступ владельца, не ключ deploy): `cd /opt/gorky_code && git checkout <хороший-sha> && make shared-up`. Но следующий автодеплой вернёт `main`, поэтому после этого всё равно сделать `revert` в `main`.
- База: миграции только добавляют, данные пользователя 1 восстанавливаются идемпотентным импортом CSV при старте.

### 6.3. Если стенд упал

По шагам, на сервере в `/opt/gorky_code`:

```bash
C="docker compose -f docker-compose.yml -f docker-compose.shared.yml"
$C ps                                   # кто не Up / unhealthy
curl -s http://127.0.0.1:8080/health    # мимо nginx: db, stt, tts, impl, seed_items
$C logs --tail=200 api                  # ошибка старта, миграции, «seed:»
$C logs --tail=100 caddy db             # прокси и база
sudo nginx -t && systemctl status nginx # внешний nginx и сертификат
```

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| api не стартует, в логе `APP_ENV=prod: …` | сработали prod-проверки (секрет, пароль БД, ICS-токен) | поправить `.env`, `$C up -d` |
| compose: «Задайте SESSION_SECRET» | нет секрета в `.env` | добавить (`openssl rand -hex 32`), старая версия всё это время работала |
| api `unhealthy`, перезапускается | модели не влезли в память (OOM) или долго грузятся | `docker stats`, профиль int8 из `.env.example`, `API_MEM_LIMIT` |
| `/health`: `seed_items: 0` | CSV не загрузился | `$C logs api \| grep seed`, `make seed` |
| `/health`: `db` не `ok` | база не поднялась | `$C logs db`, место на диске `df -h` |
| сайт 502 от nginx | стек не слушает 127.0.0.1:8080 | `$C ps`, `$C up -d` |
| 429 у всех | сработал лимит (кто-то спамит) | подождать `Retry-After`; смотреть access-лог nginx |
| смоук красный на чате (401) | вход не работает, cookie | проверить `POST /api/session` вручную |

Потом: `./deploy/smoke.sh https://voice.planimetrika.online`. На защите, если стенд не поднимается за пару минут, — показываем **видео демо** и локальный запуск `make up`.

## 8. Вопросы жюри и ответы

**1. Как вы делили работу?**
По частям архитектуры из ТЗ: голос, понимание речи и LLM, бизнес-логика, хранение, плюс интерфейс, качество и продукт. У каждого направления своя папка и ветки, общий контракт `contracts.py` и заглушки с первого дня. Поэтому шесть человек работали параллельно, а в `main` сливала только интеграция после зелёных проверок.

**2. Как гарантируете, что всё работает?**
Четыре уровня. Эталон из 100 фраз — 100%. 583 каверзные реплики — 92% без LLM, на 30 свежих фразах 25/30. Живые логи стенда превращаются в тесты. Слепой тест на людях, которые проект не видели. Плюс CI на каждый коммит и смоук после каждого деплоя. Каждая цифра воспроизводится командой `make`.

**3. Что будет, если стенд упадёт на защите?**
Деплой идёт только после зелёного CI, после него — смоук. Небезопасная или неполная конфигурация не стартует, и тогда продолжает работать старая версия. Откат — `git revert` в `main`, дальше автоматически. На защите есть видео демо и локальный запуск одной командой.

**4. Как защищены данные пользователей?**
Пользователя определяет сервер по подписанной HttpOnly-cookie, клиент её не подделает. Каждый запрос к базе фильтруется по пользователю. LLM не видит идентификаторов, удаление — одна запись и только после подтверждения. База наружу не открыта, ключи только в `.env` на сервере, история проверена gitleaks. Логи реплик маскируются и лежат в отдельном приватном репозитории.

**5. Проверяли ли безопасность?**
Да, отдельным направлением: 19 пунктов, 5 высоких (подмена пользователя, аудио-бомба, нет лимитов, ключ деплоя с root, опасный harden-скрипт). Все закрыты в коде, на каждый есть тест в `backend/tests/security/`. Отчёт — `docs/security/REPORT.md`.

**6. Почему Docker Compose, а не Kubernetes?**
Один сервер и один процесс API: голосовые модели живут в памяти, второй экземпляр удвоил бы RAM. Kubernetes добавил бы сложность без пользы для прототипа. Compose даёт то же, что нужно: воспроизводимые образы, healthcheck, лимиты ресурсов, перезапуск. Для масштаба переход естественный: образы те же, состояние диалога и лимиты выносятся в Redis.

**7. Как использовали ИИ-инструменты?**
Да, ТЗ это разрешает. ИИ писал код по нашим заданиям, каждое направление — в своём диалоге. Архитектура, контракт, разбиение на зоны, решения и критерии приёмки — наши. Ничего не попадало в `main` без линтеров, типов, тестов и eval. Именно поэтому система проверки получилась строже обычной: мы не доверяли коду «на слово».

**8. Сколько стоит хостинг?**
Стенд работает «соседом» на уже оплаченном VPS вместе с другим приложением, отдельного сервера под него нет. Лёгкий профиль (GigaAM int8, озвучка браузером) укладывается примерно в 1,1 ГБ памяти API и рассчитан на сервер 4 ГБ, 2 vCPU. Распознавание на своём сервере — нет оплаты за минуту. Экономика на пользователя — вопрос к капитану (около 20 ₽ в месяц на LLM).

**9. Как устроен деплой?**
Пуш в `main` → CI → при зелёном Deploy по SSH. Ключ GitHub на сервере может только запустить один скрипт: подтянуть `main` и пересобрать контейнеры. Shell не даёт, проброс портов не даёт. Отпечаток сервера проверяется, action закреплён по SHA. После деплоя — смоук.

**10. Почему эталону 100% можно верить, если вы его сами написали?**
Ожидаемые ответы вычислены скриптом по CSV, а не руками. Но мы согласны, что своего набора мало. Поэтому есть каверзные реплики (было 50%), проверка на свежих фразах и слепой тест. 100% на эталоне — это минимальная планка, а не главная цифра.

**11. Что если кто-то начнёт спамить запросами?**
Лимиты на трёх слоях: nginx по IP (5 запросов в секунду, 30 реплик в минуту, 10 WebSocket), приложение по сессии (20 реплик в минуту) и по сервису (3000 в час). Аудио обрезается до 20 секунд ещё до декодирования, распознавание идёт не больше чем в два потока. У контейнеров лимиты памяти и CPU, так что соседнее приложение не страдает.

**12. Как узнаёте об ошибках на стенде?**
Каждая реплика (фраза, намерение, ответ) раз в час уходит в приватный репозиторий логов, почты и номера маскируются. Каждое утро автоматическая проверка разбирает логи, неудачные фразы становятся тестами `qa/live`. Тест с пометкой `known` падает, пока не починят, и сам показывает момент исправления.

**13. Как вы сливали работу шести человек без хаоса?**
Контракт меняет только интеграция, по запросу. Чужие папки не трогаются, находки оформляются промптом владельцу. Ветки сливаются по одной, после каждой — полный набор проверок, красное откатывается. Ежедневная проверка в 09:41 делает это автоматически и присылает сводку.

**14. Что с персональными данными и 152-ФЗ?**
Запись голоса не сохраняется: живёт во временном файле, пока идёт распознавание. С GigaAM распознавание на нашем сервере, звук никуда не уходит. Сервер в РФ. Для продукта — политика обработки ПДн и срок хранения логов. Логи в прототипе — осознанный инструмент отладки, с маскировкой.

**15. Что бы улучшили в инфраструктуре дальше?**
Сделать джоб security блокирующим и добавить сканирование образов (Trivy). Pull-модель деплоя: сервер сам забирает `main`, входящего ключа нет вовсе. Защита ветки `main` через PR с обязательным ревью. Redis для лимитов и сессий, чтобы запускать несколько экземпляров. Настоящий вход (Яндекс ID / Telegram) вместо демо-пользователей.
