Словарик терминов, которые встретятся дальше:

- **Миграция** — скрипт, который создаёт или меняет таблицы. У нас одна: `0001`. Запуск: `alembic -c app/storage/alembic.ini upgrade head`.
- **Индекс** — дополнительная структура, чтобы база находила строки, не читая всю таблицу (как алфавитный указатель в книге).
- **Лемма** — словарная форма слова: «Иваном» → «иван», «звонил» → «звонить». Делает библиотека `pymorphy3`.
- **tz-aware** — дата-время со сдвигом часового пояса (`+03:00`). «Naive» — без пояса; мы такие не принимаем.
- **Soft delete (мягкое удаление)** — запись не стирается, а помечается `deleted_at`; так её можно вернуть по «отмени».

## 1. Схема базы данных

База — PostgreSQL 16 с двумя расширениями: `vector` (pgvector, векторы) и `pg_trgm` (триграммы). Оба создаёт сама миграция (`CREATE EXTENSION IF NOT EXISTS …`). В docker используется образ `pgvector/pgvector:pg16`.

### 1.1. Таблицы

| Таблица | Зачем | Используется кодом сейчас? |
|---|---|---|
| `users` | пользователи: `id`, `name` (уникальное), `tz` (по умолчанию `Europe/Moscow`), `ics_token`, `created_at` | да (`ensure_user`, `get_or_create_user`); `ics_token` в коде пока не читается — токены ICS берутся из настройки `ICS_TOKENS` (`backend/app/config.py`) |
| `items` | все записи: задачи, напоминания, встречи | да, главная таблица |
| `actions` | журнал действий для «отмени» (undo) | да |
| `dialog_sessions` | состояние диалога | **нет** — заготовка; состояние живёт в памяти процесса (`SessionStore` в `backend/app/container.py`, ключ `(user_id, session_id)`, TTL сутки) |
| `turns` | лог ходов диалога для метрик | **нет** — заготовка; реплики стенда пишутся в отдельный репозиторий логов |

Честно говорить так: «две таблицы под диалог заложены в схеме, но в прототипе состояние держим в памяти — оно живёт сутки и не нужно после перезапуска».

### 1.2. `items` — все поля

**Содержательные поля (из контракта `Item`):**

| Поле | Тип | Зачем |
|---|---|---|
| `id` | bigint, PK | номер записи. Для пользователя 1 после импорта `id` = `id` из CSV — поэтому номера в `golden_eval.jsonl` совпадают с базой |
| `user_id` | int → `users.id`, `ON DELETE CASCADE` | чья запись. Основа изоляции (раздел 2.3) |
| `type` | text, CHECK `task/meeting/reminder` | тип записи |
| `title` | text | название, которое видит пользователь (для CSV — **исправленное**) |
| `title_original` | text | исходный текст из CSV до исправления падежей. Ничего не теряем: можно показать «как было» |
| `starts_at`, `ends_at` | timestamptz | начало и конец **встречи** |
| `due_at` | timestamptz | срок **задачи / напоминания** (точка во времени) |
| `has_time` | bool, по умолчанию `true` | `false` — назван только день («в пятницу отправить отчёт»); тогда время в `due_at` не значимо, ответ пишет «в течение дня» (`backend/app/domain/responder.py`) |
| `status` | text, CHECK `open/done/cancelled/unknown` | `open` — новая, `done` — «выполнено», `unknown` — статус неизвестен (весь импорт CSV) |
| `rrule` | text | правило повтора в формате iCalendar RRULE, напр. `FREQ=WEEKLY;BYDAY=MO` |
| `person` | text[] | люди в исходной форме: `['Иван']` |
| `organization` | text[] | компании: `['Орбита']` |
| `topic` | text | тема: «договор», «презентация», «CRM»… |
| `object` | text | объект/действие: «техническое задание», «звонок», «итоги встречи»… |
| `source` | text, CHECK `voice/text/import` | откуда запись |
| `source_ref` | text | ссылка на источник: `"csv:688"` = строка 688 из CSV. Нужна для идемпотентного импорта и чтобы у второго пользователя (с новыми `id`) можно было сопоставить запись с CSV |
| `created_at`, `updated_at` | timestamptz, `now()` | ставит база. У импортированных записей `created_at` = момент импорта (в CSV даты создания нет) |
| `deleted_at` | timestamptz | мягкое удаление: не `NULL` — запись удалена, но её можно вернуть |

**Поисковые поля (их заполняет репозиторий, пользователь их не видит):**

| Поле | Как получается | Зачем |
|---|---|---|
| `person_norm` | `norm_person()` из `text.py`: лемма + нижний регистр + ё→е («Иваном» → `иван`) | быстрый точный фильтр «записи с Иваном» |
| `organization_norm` | `fold()` — нижний регистр, ё→е (`орбита`, `партнер`) | фильтр по компании |
| `search_text` | `search_text()` из `text.py`: леммы заголовка, темы, объекта, людей, компаний **плюс все синонимы**. Пример для #1: `подготовить техзадание техническое_задание техничка тз` | по нему считается «покрытие» и ищут триграммы |
| `search_tsv` | **вычисляемая колонка** (`GENERATED … STORED`): `setweight(to_tsvector('russian', title), 'A') ‖ setweight(to_tsvector('simple', search_text), 'B')` | полнотекстовый поиск (FTS). Вес A — слова заголовка, B — леммы и синонимы |
| `embedding` | `vector(1024)` — эмбеддинг текста `title + topic + object + люди + компании` (`embedding_text()` в `embeddings.py`) | поиск «похожих по смыслу» (k-NN) |
| `sort_at` | вычисляемая: `coalesce(starts_at, due_at)` | «момент записи» одним полем: для диапазонов, фильтра прошлое/будущее и сортировки |

Ограничения (CHECK): тип, статус, источник из списка; `ends_at >= starts_at`.

Как пересчитываются поисковые поля: в `create` и `update` вызывается `fill_search_fields(row, embedder)` (`repository.py`) — пересчитывает `person_norm`, `organization_norm`, `search_text`, `embedding`. `search_tsv` и `sort_at` база считает сама. После правки словаря синонимов нужно `python -m app.cli reembed` — он пересчитывает поля у всех записей (иначе в базе останется `search_text` по старому словарю).

### 1.3. Индексы и зачем каждый

| Индекс | Вид | Для какого запроса |
|---|---|---|
| `ix_items_user_id` | B-tree `(user_id)` | все записи пользователя |
| `ix_items_user_starts` | B-tree `(user_id, starts_at)` | встречи пользователя в периоде, конфликты |
| `ix_items_user_due` | B-tree `(user_id, due_at)` | задачи в периоде |
| `ix_items_user_sort_alive` | B-tree `(user_id, sort_at) WHERE deleted_at IS NULL` — **частичный** | «что у меня на неделе», фильтр прошлое/будущее; частичный — в индекс не попадают удалённые, он меньше |
| `ux_items_user_source_ref` | уникальный `(user_id, source_ref) WHERE source_ref IS NOT NULL` | гарантия, что одна строка CSV не импортируется дважды одному пользователю |
| `ix_items_tsv` | **GIN** по `search_tsv` | полнотекстовый поиск `search_tsv @@ tsquery` |
| `ix_items_title_trgm`, `ix_items_search_trgm` | **GIN + `gin_trgm_ops`** по `title` и `search_text` | поиск с опечатками через триграммы (`word_similarity`) |
| `ix_items_person_norm`, `ix_items_org_norm` | **GIN** по массивам | фильтр «массив пересекается»: `person_norm && ['иван']` |
| `ix_items_embedding` | **HNSW**, `vector_cosine_ops` | быстрый поиск ближайших векторов по косинусному расстоянию |
| `ix_actions_user_created` | B-tree `(user_id, created_at)` | последние действия пользователя для undo |

Что это за виды:
- **B-tree** — обычный «отсортированный указатель»: быстро для `=`, `<`, `>`, диапазонов.
- **GIN** (Generalized Inverted Index) — «обратный индекс»: для каждого слова/элемента хранит список строк, где оно есть. Подходит для текста, массивов и триграмм.
- **HNSW** (Hierarchical Navigable Small World) — граф «соседей» для приближённого поиска ближайших векторов: не сравнивает запрос со всеми векторами, а «перепрыгивает» по графу.

### 1.4. Как поля ТЗ ложатся на схему

| Поле из ТЗ | Колонка | Комментарий |
|---|---|---|
| Тип (задача / встреча / напоминание) | `items.type` | в CSV типа нет — выводим (раздел 3) |
| Название | `items.title` (+ `title_original`) | у CSV исправляем падежи, исходник храним |
| Дата и время | встреча: `starts_at` + `ends_at`; задача/напоминание: `due_at` + `has_time` | у CSV `date` + `time` → одна точка |
| Дата создания | `items.created_at` (ставит база) | в CSV её нет: у импорта = момент импорта |
| Статус | `items.status` | в CSV нет: `unknown` — честно «не знаем», а не выдумываем `open` или `done` |

### 1.5. Хранение времени

- **Встреча** — интервал `starts_at` / `ends_at`. Длительность по умолчанию: встреча 60 минут, демо 30 (`DEFAULT_DURATION_MIN` в `enrich.py`; для голосовых — `default_duration_min` в домене).
- **Задача и напоминание** — точка `due_at`. Если время не названо — `has_time=false`.
- **Только tz-aware.** Функция `_tz()` в `repository.py`: если `datetime` без пояса — `ValueError("naive datetime: в хранилище только tz-aware время")`; иначе переводит в `Europe/Moscow` (`DEFAULT_TZ` из `storage/config.py`). Колонки — `timestamptz`, PostgreSQL хранит момент в UTC.
- Зачем так строго: ошибка «на 3 часа» (UTC против МСК) — самая частая в календарях. Если naive не пускать в базу, такая ошибка падает сразу, а не тихо сдвигает встречи.

### 1.6. Журнал `actions` (undo)

Поля: `user_id`, `session_id`, `kind` (`create / update / complete / delete`), `item_id`, `before` и `after` — JSON-снимки `Item` до и после, `undone_at`.

Как работает «отмени» (`ItemService._undo_one` в `backend/app/domain/service.py`):
- было `create` → `soft_delete` созданной записи;
- было `delete` → `restore` (снимаем `deleted_at`);
- было `update` / `complete` → `repo.update(action.before)` — возвращаем снимок «до»;
- затем `mark_undone` (ставит `undone_at`). Отменить можно только действие своей сессии.

## 2. Репозиторий

### 2.1. Методы контракта `ItemRepository` (`backend/app/contracts.py`)

| Метод | Что делает `SqlItemRepository` |
|---|---|
| `create(item)` | вставляет строку; `id`, `created_at`, `updated_at` из входа **игнорирует** — их ставит база; считает поисковые поля |
| `get(user_id, item_id)` | одна запись, только своего пользователя и не удалённая |
| `update(item)` | `SELECT … FOR UPDATE` (блокировка строки) по `id` **и** `user_id`, переписывает поля, `updated_at = now()`, пересчитывает поисковые поля; нет записи — `KeyError` |
| `soft_delete(user_id, item_id)` / `restore(...)` | ставит / снимает `deleted_at` (через `_set_deleted`) |
| `list_range(user_id, start, end, type=None)` | полуоткрытый интервал `[start, end)`: запись, чей `sort_at` внутри; встреча, пересекающая период; повторяющаяся серия, начатая до `end` (развёртку делает домен — `expand_occurrences`) |
| `find_overlaps(user_id, start, end)` | для конфликтов: встречи, пересекающие интервал (без `ends_at` считаем 60 мин; **смежные не конфликтуют**), задачи/напоминания со временем внутри интервала; повторяющиеся встречи разворачиваются; удалённые и `cancelled` не берутся |
| `log_action(ActionRecord) -> id` | пишет в `actions`, возвращает `id` |
| `get_action(user_id, action_id)` | читает действие и превращает JSON обратно в `Item` |
| `mark_undone(user_id, action_id)` | ставит `undone_at` |

Сверх контракта: `ensure_user` (пользователь по id или имени, создаёт при необходимости), `get_or_create_user`, `get_many`.

### 2.2. Хранилище в памяти

Есть второй режим — `STORAGE_IMPL=memory` (по умолчанию в `Settings`): `InMemoryRepository` в `backend/app/fakes/repository.py`. Он грузит тот же CSV **той же функцией** `enrich.csv_item`, поэтому данные одинаковые. Поиск в памяти — `InMemorySearchEngine` (`backend/app/storage/memory.py`), он же `FakeSearchEngine`. На стенде и в `make eval-real` — PostgreSQL.

### 2.3. Изоляция пользователей

- В **каждом** запросе репозитория и поиска есть условие `ItemRow.user_id == user_id` (см. `get`, `update`, `_set_deleted`, `list_range`, `_alive`, `get_action`, `mark_undone`, `HybridSearchEngine._filters`). Чужую запись нельзя ни прочитать, ни изменить: `update` чужого `id` даст `KeyError`.
- Откуда берётся `user_id`: из подписанной cookie `pomnyu_session` (`backend/app/api/session.py`), а не из заголовка клиента — подделать нельзя.
- Состояние диалога тоже ключуется `(user_id, session_id)` — чужой `session_id` не продолжит чужой диалог.
- Уникальный индекс `(user_id, source_ref)` — импорт одного CSV разным пользователям не конфликтует.

## 3. Данные организаторов (CSV)

Файл `data/voice_assistant_events_1000.csv`: 1000 строк, 4 колонки — `id, date, time, text`. Даты с 2024-01-07 по 2027-12-31.

### 3.1. Что с данными не так

1. **Нет типа, статуса и даты создания** — а в ТЗ они есть у каждой записи.
2. **Около 25 шаблонов** — текст сгенерирован по образцам вроде «Позвонить ‹имя›», «Встреча с ‹имя› по ‹теме›», «Созвон с ‹компания› по ‹теме›». Самые частые: «Собрать обратную связь по …» (62), «Проверить сроки по …» (61), «Проверить статус задачи по …» (60), «Подготовиться к встрече с …» (60). Людей 10, компаний 8, тем 10.
3. **Сломанные падежи в 313 строках (31%)** — имя подставлено в творительном падеже везде: «Позвонить Иваном», «Отправить договор Марией», «Напомнить Анной про мобильному приложению», «Обсудить договору с Алексеем», «Созвон с Стартом», «Обсудить бюджет по бюджету».
4. BOM в начале файла (первая колонка читалась бы как `﻿id`) — снимаем `encoding="utf-8-sig"` в `read_csv`.

### 3.2. Как разбираем: `enrich()` в `backend/app/storage/enrich.py`

Разбор **шаблонами** (регулярными выражениями), а не нейросетью: детерминированно (каждый раз одинаково) и проверяемо тестами (`backend/tests/storage/test_enrich.py`). Словари форм — в `text.py`: `PERSON_FORMS` (10 имён × 5 падежей), `ORG_FORMS` (8 компаний, именительный + творительный), `TOPIC_FORMS` (тема → форма «по чему»), `TOPIC_ACC` (винительный), `OBJECT_FORMS`.

Каждый шаблон возвращает `Enriched`: тип, исправленный заголовок, исходник, люди, компании, тема, объект, что исправили (`text_issue`: `case` / `preposition` / `tautology`), длительность.

**Тип:**
- `Встреча с … по …`, `Созвон с … по …`, `Демо проекта по …`, `Провести планёрку по …` → `meeting`;
- `Напомнить … про …` → `reminder`;
- остальное → `task`.
- Если шаблон не узнан — `_fallback()`: тип по первому слову, люди и компании по словарю, тема по вхождению. **На нашем CSV fallback не срабатывает ни разу** (проверено: все 1000 строк попали в шаблоны), но он страхует от нового файла.

Итог (проверено запуском `enrich` по всем строкам): **задачи 761, встречи 186, напоминания 53**; исправлено **313** заголовков: падеж — 300, предлог «с → со» — 8, тавтология — 5.

**Как чинится падеж.** Шаблон знает, какой падеж должен быть после глагола: «Позвонить» + дательный, «для» + родительный, «про» + винительный. Имя из творительного находим по обратному словарю `_PERSON_INS` и берём нужную форму из `PERSON_FORMS`. Тему «про мобильному приложению» переводим в винительный через `TOPIC_ACC`.

**Люди / компании / темы** берутся из групп регулярного выражения, приводятся к именительному («Иваном» → «Иван») и пишутся в `person`, `organization`, `topic`, `object`. Если объект совпадает с темой («договор», «презентация») — он становится и темой (`_topic_of_object`).

### 3.5. Импорт: `python -m app.cli import-csv … --user 1`

`import_csv()` в `backend/app/cli.py`:
1. `ensure_user` — пользователь по id (строка в `users` создаётся при необходимости) или по имени.
2. **Быстрый путь идемпотентности:** читает все `source_ref` пользователя; если все `csv:<id>` уже есть — сразу выходит. Проверено на нашей базе:
   ```
   {"skipped_existing": 1000, "inserted": 0, "user_id": 1}
   ```
   Поэтому импорт безопасно запускать на каждом старте API — так и делает `backend/docker-entrypoint.sh`.
3. Иначе — `build_rows` (обогащение), `_embed_batch` (поисковые поля и векторы пачкой), повторная проверка `source_ref` уже внутри транзакции, вставка.
4. `id` из CSV сохраняются, если свободны (первый пользователь). Если заняты (второй пользователь) — база выдаёт новые, связь через `source_ref`.
5. `--replace` — удалить прежний импорт пользователя и залить заново; `--new-ids` — не сохранять id.
6. В конце сдвигается последовательность `items.id` (`setval`), чтобы новые записи не столкнулись с id из CSV.

Защита от дублей двойная: проверка в коде + уникальный индекс `ux_items_user_source_ref` в базе.

## 4. Поиск

### 4.1. Четыре понятия простыми словами

- **FTS (полнотекстовый поиск)** — база разбивает текст на слова, приводит к основе и ищет запись, где есть слова запроса. `to_tsvector('russian', 'Встреча с Иваном')` → `'встреч' 'иван'`. Запрос — `tsquery`, совпадение — оператор `@@`. Быстро благодаря GIN-индексу.
- **Триграммы** — текст режется на кусочки по 3 буквы: «орбита» → `орб, рби, бит, ита…`. У «арбита» и «орбита» большинство кусочков общие → слова похожи. Так ловятся опечатки и ошибки распознавания речи. Функция `word_similarity` из `pg_trgm`.
- **Эмбеддинг** — список из 1024 чисел, «координаты смысла» текста. Близкие по смыслу тексты — близкие векторы. Близость — косинусное расстояние (`<=>` в pgvector): 0 — одинаково, 2 — противоположно. **k-NN** — найти k ближайших векторов.
- **RRF (Reciprocal Rank Fusion)** — способ слить несколько списков: каждой записи даётся сумма `1 / (k + место)` по всем спискам, обычно k = 60. **Важно:** RRF был в первой версии поиска, но в коммите `88af022` (storage/v3) его убрали; строка «→ RRF (k = 60)» осталась только в `backend/app/storage/README.md`. В текущем коде три списка кандидатов **объединяются**, а порядок решает покрытие смысловых групп и время (ниже). На защите говорить точно: «три источника кандидатов → объединение → ранжирование по покрытию и времени». Почему отказались: RRF ставит выше то, что выше в «чужих» списках (например, похожее по вектору), а нам нужен понятный порядок «сначала то, что точно про запрос, потом по времени».

### 4.2. Где что лежит

- `ranking.py` — **весь алгоритм** без SQL: разбор запроса (`plan_query`), фильтры (`passes_filters`), покрытие (`coverage`), уровни и порядок (`order`, `rank_matches`, `rank_all`).
- `search.py` — `HybridSearchEngine`: те же фильтры в SQL (`_filters`) и три запроса-кандидата (`_candidate_queries`), затем `ranking.rank_matches`.
- `memory.py` — `InMemorySearchEngine`: кандидаты = все записи пользователя, прошедшие фильтры, затем тот же `rank_matches`.

Вход поиска — `Slots` от NLU (`query`, `type`, `participants`, `organization`, `status`, `tense`, `when`); выход — список `(Item, score)`.

### 4.3. Алгоритм по шагам

**Шаг 1. Разбор запроса (`plan_query`).**
- Текст = `slots.query` или `slots.title`.
- `extract_entities()` (`text.py`) достаёт имена и компании, даже если NLU их не выделил: известная форма имени в любом регистре; компания — с заглавной буквы или после предлога («со стартом» из распознавания); **одна опечатка** допускается (`fuzzy_ok`: 1 правка от 5 букв, 2 — от 9) → «с арбитой» → Орбита; имя, разбитое распознаванием, склеивается в `words()` («и ваном» → «иваном»); незнакомое слово с заглавной, которое `pymorphy3` помечает как имя (`Name`), тоже становится человеком («Петром» → Петр).
- Аббревиатуры по буквам нормализуются (`normalize_spoken`): «тэ зэ» → ТЗ, «си ар эм» → CRM, «ка пэ» → КП.
- Остальные слова → леммы без служебных (`STOPWORDS`: «найди», «задача», «когда-то», «её»…), без слов времени (`TIME_WORDS`) и без имён/компаний.

**Шаг 2. Время запроса (tense).** Берётся `slots.tense` (`past` / `future` / `any`). Если NLU оставил `any`, а в запросе есть «старую», «прошедшие», «давнюю», «прежние» (`PAST_WORDS`) или «будущие», «предстоящие», «ближайший» (`FUTURE_WORDS`) — время берётся из них (`tense_of_words`). Эти слова — не тема и в покрытии не участвуют.

**Шаг 3. Смысловые группы и синонимы.** Каждая оставшаяся лемма превращается в **группу** — само слово + синонимы из `backend/app/nlu/synonyms.yml` (`query_group`):
- `phrases` — симметричные группы: `техническое задание: [тз, техзадание, тех задание, техничка, тэ зэ, …]`; двухсловные варианты склеиваются в один токен `техническое_задание`;
- `expand` — только в одну сторону, для запроса: `деньги: [бюджет, смета]`;
- `verbs` — разговорный глагол → глагол заголовков («звонил» → позвонить);
- `types` — слово-тип даёт мягкую подсказку типа («встреча», «созвон» → `meeting`);
- `organizations`, `people` — сущности.
Слова, которые NLU подставил из одного правила `expand` («бюджет смета»), сливаются в одну группу «или» (`_merge_expanded`). Если файла словаря нет — поиск работает без синонимов, с предупреждением в логе.

**Шаг 4. Фильтры (жёсткие).** `passes_filters` / SQL-двойник `_filters`: свой `user_id`, не удалённая, не `cancelled` (если статус не спросили явно), тип, люди (`person_norm && …`), компания, прошлое (`sort_at < now`) или будущее (`sort_at >= now`), период `when`.

**Шаг 5. Пустой запрос.** Если нет ни групп, ни людей, ни фильтров — пустой ответ (`is_constrained`). Если групп нет, но есть фильтры («записи Елены») — все прошедшие фильтры записи одним уровнем со score 1.0 (`rank_all`, `SCORE_FILTER_ONLY`).

**Шаг 6. Кандидаты (только PostgreSQL), внутри фильтров:**
1. FTS: `to_tsquery('simple', группы через |)` ‖ `to_tsquery('russian', сырые леммы)`, сортировка по `ts_rank_cd`, до 200 (`CANDIDATES_PER_LIST`);
2. триграммы: `word_similarity(первые слова групп, search_text) >= 0.35` (`TRIGRAM_MIN`), до 200;
3. k-NN: эмбеддинг текста всех групп, косинусное расстояние `<= 0.75` (`VECTOR_MAX_DISTANCE`), до 50 (`VECTOR_CANDIDATES`).
Кандидаты объединяются по `id`. Они отвечают **только за полноту отбора**; кто выше — решает шаг 7.

**Шаг 7. Покрытие (`coverage`).** Для каждого кандидата — доля групп, найденных в его `search_text`. Слово группы «найдено», если: есть точно; **или** слово ≥ 6 букв и токен записи начинается с тех же 6 букв (так «подготовка» находит «подготовиться»); **или** похоже с опечаткой (`fuzzy_ok`, «презинтация» ~ «презентация»).

**Шаг 8. Уровни и «не нашёл» (`rank_matches`).**
- Ни одна группа не совпала: если названы человек/компания — все записи по ним, score 0.5 (`SCORE_STRUCTURE_ONLY`); иначе — пусто.
- Совпало **только слово-тип** («встреча»), а предмет («с дизайнером») — нет: пустой ответ, честное «не нашёл».
- Записи с покрытием ниже половины лучшего отбрасываются.
- **score** = покрытие − 0,01, если тип записи не совпал с подсказкой из запроса (`TYPE_MISS_PENALTY`). Штраф меньше шага покрытия, поэтому никогда не поднимает запись выше более полной. Это **уровень**, а не позиция: у одинаково подходящих записей он одинаковый.
- Если в лучшем уровне ≥ 5 записей (`TOP_TIER_ALONE`), нижние уровни не отдаются.

**Шаг 9. Порядок (`order`).** Сначала score, потом время:
- `past` — **свежие первыми** (поэтому «когда была встреча с Иваном» отвечает последней);
- `future` — **ближайшие первыми**;
- `any` — ближайшие к «сейчас» в обе стороны (будущее чуть приоритетнее при равенстве);
- при полном равенстве — по `id`.

**Шаг 10. Обрезка** до `limit` (по умолчанию 20).

### 4.4. Паритет PostgreSQL и памяти

`backend/tests/storage/test_search_parity.py` гоняет одни и те же запросы (все поисковые фразы эталона без `history` + дополнительные вроде «Найди встречу, старую», «Покажи будущие встречи») через `HybridSearchEngine` и `FakeSearchEngine` и требует **те же записи, в том же порядке, с теми же баллами** — в трёх вариантах: со слотами от NLU, по сырому запросу без NLU и только со структурными слотами. ### 4.5. Эмбеддер

**`EMBEDDINGS_MODEL=hash` (по умолчанию, `HashEmbedder`)** — не нейросеть. Как устроен:
1. текст → леммы → **плюс синонимы** (`expand`);
2. каждая лемма даёт признак `w:<лемма>` (вес 1.0) и признаки символьных триграмм `c:<3 буквы>` (вес 0.3);
3. признак хешируется (`blake2b`) в одну из 1024 позиций со знаком ±1 («feature hashing»);
4. вектор нормируется до длины 1.
Что это даёт: «ТЗ» и «техническое задание» — **одинаковый** вектор (оба раскрываются в одну группу синонимов; проверено: расстояние от запроса «тз» до «Подготовить техническое задание» и до «Подготовить ТЗ» одинаковое — 0,082), опечатки ловятся триграммами. Чего не даёт: смысла за пределами словаря — «договор» и «соглашение» он не свяжет, если их нет в одной группе.

**`EMBEDDINGS_MODEL=deepvk/USER-bge-m3` (`SentenceTransformerEmbedder`)** — настоящая нейросетевая модель для русского, тоже 1024 измерения (код проверяет размерность и падает, если не 1024). Ловит смысловую близость без словаря. Цена — по README и `.env.example` **ещё около 2 ГБ памяти** и зависимость `sentence-transformers` (extra `embeddings` в `backend/pyproject.toml`). Включение:
```bash
EMBEDDINGS_MODEL=deepvk/USER-bge-m3   # в .env
python -m app.cli reembed             # пересчитать векторы всех записей
```

**Честно на защите:** на стенде работает `hash` (на сервере 4 ГБ, там же GigaAM для распознавания). «Смысл» на стенде дают словарь синонимов и морфология, а векторный канал — страховка по опечаткам и синонимам. Recall@5 = 100% получен **без** нейромодели. Архитектура готова к нейромодели одной переменной.

 1.000  #672   2026-09-19 17:00  [task] Проверить договор по интеграции
 1.000  #670   2026-09-12 11:45  [meeting] Встреча с Марией по договору

Почему: «я», «когда-то», «ставил», «задачу», «найди», «её» — служебные. Группа `{договор, договорчик, контракт}`. Прошлое → из 91 записи с «договором» остаются 63 прошедшие, свежие первыми. ### 5.4. «Найди всё про ТЗ» (`--tense any`)

```
 1.000  #679   2026-09-29 12:15  [task] Проверить техническое задание по бюджету
 1.000  #662   2026-08-29 20:00  [task] Отправить техническое задание Елене
 1.000  #644   2026-08-08 08:00  [task] Проверить техническое задание по аналитике
 … всего 27
```
Почему: «тз» → группа `{тз, техзадание, техническое_задание, техничка}`. В FTS это `(техзадание) | (техническое <-> задание) | (техничка) | (тз)` — `<->` значит «два слова подряд». В `search_text` каждой записи с «техническим заданием» уже лежит `тз` (синонимы добавлены при сохранении), поэтому все 27 находятся тремя каналами сразу; векторное расстояние у них 0,082. Эталон q28 — **27** id. В заголовках CSV аббревиатуры «ТЗ» нет вообще — нашли только благодаря словарю.

### 5.5. «созвон с арбитой» (`--tense any`)

```
 1.000  #698   2026-10-29 15:30  [meeting] Созвон с Орбитой по презентации
 1.000  #774   2027-02-02 10:45  [meeting] Созвон с Орбитой по интеграции
 1.000  #578   2026-05-14 18:00  [meeting] Созвон с Орбитой по аналитике
```
Почему: «арбитой» стоит после предлога «с», в словаре его нет → `_fuzzy_lookup` сравнивает с формами компаний: «арбитой» ↔ «орбитой» — одна замена, слово 7 букв → Орбита. Это фильтр `organization_norm && ['орбита']`. Группа `{созвон}` + подсказка `meeting`. `any` → ближайшая к «сейчас» — 29.10. Эталон q88 «созвон с арбитой когда» ждёт `answer_id = 698` — на 1-м месте.

### 5.6. Бонус: честное «не нашёл»

`Найди встречу с Петром` → `ничего не найдено`. «Петром» стал фильтром по человеку (`Name` у pymorphy3), а записей с Петром нет → пусто. Без этого правила поиск отдал бы «какие-нибудь встречи», что хуже, чем честный отказ (эталон q30, q85).

## 6. Метрики качества

### 6.1. Эталонный набор: `backend/eval/golden_eval.jsonl`

- **100 фраз**, у всех «сейчас» = `2026-10-21T14:00:00+03:00` (среда).
- q01–q34 — исходный набор; дальше — расширение. Категории: search 29, create 23, list 22, update 7, clarify 6, conflict 4, delete 3, smalltalk 3, complete 2, undo 1.
- Теги срезов: `tz_original` (14 фраз ТЗ дословно), `paraphrase`, `colloquial`, `asr_noise` (ошибки распознавания), `typo`, `synonym`, `case_mismatch`, `multi_turn` и др.
- `history` — реплики, которые прогоняются в той же сессии до проверяемой (многоходовые диалоги).
- `expected` — что должно получиться: `intent`, `type`, `title`, `datetime`/`due`, `conflicts_with_ids`, `missing` (что уточнить), `ids` (точный набор для списков), `relevant_ids` и `answer_id` (для поиска), `target_id` (для правки).

**Как вычислены ожидания.** По `golden_eval_format.md` — скриптом по исходному CSV, а не руками. Самого генератора в репозитории нет (он делался в чате проекта), но любое ожидание проверяется по CSV за минуту. Проверено 25.10: q20 = все 103 строки со «презентац»; q21 = 63 прошедшие строки с «договор»; q28 = 27 строк с «техническое задание» — всё совпадает с `relevant_ids`.

Правила прогона (`golden_eval_format.md`): каждая строка в чистой среде; даты сравниваются в Europe/Moscow до минуты; для срока без времени допустимо 23:59; политики дат («в 3» → 15:00, «вечером» → 19:00, «до конца недели» → вс 23:59 и т. д.).

### 6.2. Как устроен прогон: `backend/eval/run_eval.py`

**Sandbox и клоны пользователя.** «Чистая база на каждую строку» дорого (импорт ~3 с × 100). Поэтому:
1. `Sandbox.setup` — шаблон: засеянный пользователь 1, если его импорт не тронут (все 1000 строк с `updated_at = created_at` и не удалены), иначе свежий импорт во временного пользователя;
2. `Sandbox.clone` — новый пользователь и копия всех записей шаблона одним `INSERT … SELECT` (~50 мс). Возвращает соответствие «новый id → id из CSV» через `source_ref`;
3. строки, которые могут менять данные (create/update/…/с `history`), получают **свежий клон**; строки только для чтения (list/search/smalltalk без history) делят один;
4. в конце все временные пользователи удаляются (`teardown`).
Для памяти — `MemorySandbox`: новый контейнер с CSV на каждую строку.

Режимы `--target`: `container` (по умолчанию: всё как в `.env`), `orchestrator`, `http` (через `/api/chat` с заголовком `X-Freeze-Now`), `search` (только поиск, слоты строит простой `baseline_slots` — время глагола и «в этом/прошлом году»).

Команды: `make eval` (заглушки, без БД), `make eval-real` (настоящие модули + PostgreSQL + порог `--min-recall 0.9`).

### 6.3. Каждая метрика (функция `score()`)

| Метрика | Что значит | Как считается |
|---|---|---|
| **Task success** | сценарий выполнен целиком | все проверки строки истинны |
| **Точность интента** | NLU понял, что хотят | `debug.intent` == ожидаемому |
| **Точность даты и времени** | запись создана на нужный момент | `starts_at`/`due_at` в МСК до минуты; для «только дата» — день совпал, время нет или 23:59 |
| **Точность слотов** | тип, название, длительность, повтор | тип совпал; название после `norm_title` (нижний регистр, ё→е, без знаков) — в списке допустимых; `ends_at − starts_at`; RRULE как множество частей |
| **Списки за период** | «что у меня в пятницу» | **точный** набор id (не больше и не меньше); пустой период → допустимо предложить `nearest_id` |
| **Recall@5** | нужное есть в первых пяти | `|top-5 ∩ relevant| / min(5, |relevant|)` (`metrics.recall_at_k`). Делитель `min(5, …)`: при 103 релевантных идеальная выдача = 1.0, а не 5/103 |
| **Recall@5 q19–q30 (критерий)** | то же на 11 исходных поисковых строках | отдельный короткий прогон **слоя поиска без NLU** (`search_gate`) — не зависит от того, какой NLU подключён |
| **MRR** | насколько высоко первая нужная | среднее `1 / место первой релевантной` (`reciprocal_rank`) |
| **«Когда…»: top-1** | на вопрос «когда» назвали верную запись | `ranked[0] == answer_id` |
| **Честное «не нашёл»** | если искать нечего — пусто | для `relevant_ids = []`: выдача пустая |
| **Уточнения** | спросил, когда нужно, и не спросил, когда не нужно | `action == clarify` ровно когда `missing` не пуст |
| **Конфликты** | найдены и нет ложных | при ожидаемом конфликте `action == conflict` и все `conflicts_with_ids` в ответе; при пустом списке — конфликта нет |
| **Правка / выполнено / удаление** | изменили нужную запись | первая запись ответа = `target_id`; новое время совпало; удаление — только после подтверждения; для неоднозначных — любой из `accept` |
| **Верное действие** | confirm, undo, smalltalk | `reply.action` == ожидаемому |
| **Задержка p50 / p95** | скорость ответа | перцентили методом nearest-rank |

**Что это.** 583 сценария «как люди говорят голосом», на которых ассистент может ошибиться. 5 файлов по задачам ТЗ: `record_task.jsonl` (121), `record_meeting.jsonl` (116), `upcoming.jsonl` (117), `find_old.jsonl` (114), `correct.jsonl` (115). **Оси** (что ломаем): `word_order` (порядок слов), `colloquial_time` («полчетвёртого», «к обеду»), `asr_cut` (потерянный первый слог: «помни», «реноси»), `numbers_words`, `fillers_slang` (паразиты, мат), `self_correction` («в среду, ой нет, в четверг»), `two_commands`, `context` («её», «а на завтра?»), `tense` («старую», «та, что была»), `polite_indirect` («не могли бы вы…»), `nonsense` (бессмыслица), `stand_live` (реальные реплики тестировщиков со стенда). 74 сценария многоходовые.

**Формат строки:** `id`, `task`, `axis`, `turns` (реплики одной сессии, оценивается последняя), `freeze_now`, `expect`, `note`. В `expect` — только то, что однозначно: `intent`, `action` (список допустимых), `type`, `date`, `time`, `title_contains`, `title_not`, `tense`, `must_not` (запрещённые операции), `min_items`/`max_items`, `reply_has`/`reply_not`. Конфликты и цели правки **вычисляет `build.py` по CSV**, а не автор.

**Оракулы** (`oracles()` в `backend/eval/run_adversarial.py`) — правила, которые должны выполняться для **любой** фразы, даже если автор ничего не записал:
- **O0** — не было исключения (сценарий не упал);
- **O1** — название созданной записи без мусора: не пустое, без слов-паразитов и служебных («через», «завтра», «встречу», «ой», «туда», «её»…), без мата, без пустых запятых, без даты/времени в названии;
- **O2** — ответ называет сохранённое время (если у записи есть время, оно должно быть в тексте ответа);
- **O3** — «прошлое» не возвращает будущее: если `tense = past`, в найденном нет записей позже «сейчас».
«Целиком» = все `expect` + все оракулы.

**Динамика** (`qa/adversarial/BASELINE.md`, только правила, без LLM):

|---|---|---|---|---|---|---|---|
| 24.10 00:40, `main@8fd13bc` | 50% (282/569) | 58% | 41% | 40% | 71% | 38% | — |
| 24.10 03:50, nlu/v6 + dialog/v6 + adversarial-v2 | **92% (535/583)** | 83% | 97% | 98% | 87% | 94% | **25/30** |

1. **530 сценариев, ожидания которых не менялись**: на них 52% → 90%. Это тот же экзамен с теми же ответами — рост от кода.
2. **30 свежих фраз**, которых нет в наборе и которые разработчики не видели: 25/30 (83%). Это проверка на переобучение — близко к 92%, значит, правила обобщаются.

```bash
python qa/blind/summarize.py qa/blind/results/*.csv --md qa/blind/results/SUMMARY.md
```
`summarize.py` выдаёт по задачам ТЗ, по карточкам и по устройству/обстановке: число задач, долю ✓, число ~, **«✓ с первой фразы»** (✓ и `attempts == 1`), медиану секунд и попыток, плюс таблицу неудач с дословными фразами. Строки с пометкой «техн.» в `note` (сбой сети/микрофона) не входят в медиану времени, но входят в долю успеха.

**Как подать жюри.** Две цифры по пяти задачам ТЗ: доля ✓ и «✓ с первой фразы». Выборка маленькая (3–5 человек × 2 карточки = 6–10 попыток на задачу), поэтому показывать **дробью** («7/8»), а не только процентами, и не сравнивать с 92% каверзных — это другой экзамен (живая речь незнакомых людей через микрофон). Неудачи показать честно — с дословной фразой и тем, что мы с ней сделаем.

## 7. Слабые места (говорить сами, до вопроса)

1. **Форма слова — частично через префикс.** В поиске «подготовку» находит «Подготовиться к встрече…» только благодаря правилу «первые 6 букв совпали» в `coverage` (проверено: «Найди подготовку к встрече с Вектором» → `#652 Подготовиться к встрече с Вектором`, score 0,99 — минус 0,01 за тип, потому что «встреча» подсказала `meeting`, а это задача). Минус правила — оно грубое: «найди подготовку» отдаёт и «Подготовить акт», и «Подготовить вопросы…». В диалоге при правке («перенеси подготовку к встрече…») цель ищется своими основами слов (`app/dialog/targets.py`, `app/domain/ru.py`): там «подготовку» → `подготовк`, «Подготовиться» → `подготовитьс` — не совпадают; в базовом прогоне каверзных это был провал `co-035`.
2. **Падежи имён вне словаря.** Для 10 имён из CSV все 5 падежей заданы руками (`PERSON_FORMS`), «Елены» ↔ «Еленой» работает. Для остальных — `pymorphy3`, и он ошибается: проверено `norm_person("Ани") = "ани"`, а `norm_person("Аня") = "аня"` — запись «встреча с Аней» не найдётся по «задачи Ани». Плюс опечаточная терпимость даёт ложные совпадения: «Позвонить Олегу» находит «Позвонить Ольге» («олегу» ↔ «ольгу» — одна правка, а Олега в словаре нет).
3. **Имена и компании при импорте — только из небольшого списка** (10 людей, 8 компаний в `text.py`). На нашем CSV этого достаточно (fallback не сработал ни разу), но новый файл с «Петром» или «Глобусом» даст записи без `person`/`organization` — они найдутся только текстом, без фильтра. 518 из 1000 строк вообще без людей и компаний — это свойство данных, а не ошибка.
4. **Hash-эмбеддер — не семантика.** Синонимы вне словаря он не свяжет. «Смысл» на стенде = словарь + морфология + опечатки. Нейромодель подключается одной переменной, но требует ~2 ГБ.
5. **README говорит про RRF, код — нет** (раздел 4.1). Говорить как в коде.
6. **На больших объёмах кандидатов ограничено.** FTS и триграммы берут до 200 кандидатов, вектор — до 50, отсортированных по «похожести», а при равной похожести — по `id`. Если подходящих записей у одного пользователя тысячи, порядок «свежие первыми» применяется только к попавшим в эти 200; при равном ранге в CSV меньший `id` = более старая запись. На 1000 записях не проявляется (максимум — 103 кандидата). Не замеряли.
7. **Таблицы `dialog_sessions` и `turns` не используются**, состояние диалога — в памяти процесса (теряется при перезапуске).
8. **Статус у импорта `unknown`.** Списки и поиск это не ломает, но «покажи невыполненные» по импортированным записям ничего осмысленного не даст.

## 8. 15 вопросов жюри с ответами

**1. Почему PostgreSQL, а не векторная база (Pinecone, Qdrant…)?**
Нам нужны одновременно: точные фильтры (пользователь, тип, человек, прошлое/будущее), полнотекст по-русски, опечатки и векторы — и всё в одной транзакции с CRUD и журналом undo. PostgreSQL даёт это одной базой: GIN для FTS и массивов, `pg_trgm` для опечаток, `pgvector` с HNSW для векторов. Векторная БД закрыла бы только один из трёх каналов, а данные пришлось бы синхронизировать между двумя хранилищами. На 1000 записей и даже на сотнях тысяч PostgreSQL справляется.

**2. Это настоящий семантический поиск?**
Честно: на стенде — «словарный»: морфология (леммы), словарь синонимов («мобилка» = мобильное приложение, «ТЗ» = техническое задание, «деньги» → бюджет/смета), устойчивость к опечаткам и легкий хеширующий эмбеддер. Нейросетевая модель `deepvk/USER-bge-m3` подключается одной переменной и командой `reembed`, но требует ~2 ГБ памяти, которых нет на стенде рядом с распознаванием речи. Recall@5 = 100% получен без нейромодели.

**3. Как изолированы пользователи?**
`user_id` в каждом запросе репозитория и поиска (`WHERE user_id = …`), `update` чужой записи падает с `KeyError`. `user_id` берётся из подписанной cookie, а не от клиента. Состояние диалога — по паре `(user_id, session_id)`. Внешние ключи с `ON DELETE CASCADE`.

**4. Как считали метрики? Не подогнаны ли?**
Эталон — 100 фраз, ожидания посчитаны скриптом по CSV (любое проверяется за минуту — показать на q20: 103 строки со «презентац»). Каждая строка — в чистой копии данных. Подгонку проверяли отдельно: 583 каверзные реплики с оракулами — 92%; на 530 сценариях с неизменными ожиданиями 52% → 90%; на 30 свежих фразах, которых разработчики не видели, — 25/30. Плюс слепой тест 26–27.10 на людях.

**5. Что такое Recall@5?**
Доля нужных записей среди первых пяти результатов: `|top-5 ∩ нужные| / min(5, число нужных)`. Если нужных 3 и все три в пятёрке — 1.0. Если нужных 103 — достаточно, чтобы пять первых были нужными. Пять — потому что голосом больше пяти не зачитаешь.

**6. А MRR?**
Средняя «обратная позиция» первой нужной записи: на 1-м месте — 1, на 2-м — 0,5, на 3-м — 0,33. У нас 0,98: в одной строке (q62) первой оказалась запись, которую строгий эталон не считает нужной, хотя по смыслу она подходит.

**7. Как поведёт себя на 100 тысячах записей?**
Все фильтры и поиск идут по индексам: B-tree по `(user_id, sort_at)`, GIN по тексту и массивам, HNSW по векторам — полного перебора нет. Кандидатов ограничено (200/200/50), покрытие считается в Python только по ним. Риски, которые мы видим: при тысячах одинаково подходящих записей у одного пользователя порядок «свежие первыми» работает только внутри 200 кандидатов; HNSW-индекс общий на всех пользователей, и фильтр по `user_id` после k-NN может «съесть» кандидатов. Нагрузочно не замеряли — это следующий шаг.

**8. Что было не так с данными организаторов?**
Нет типа, статуса, даты создания; 25 шаблонов; в 313 строках сломаны падежи («Позвонить Иваном»). Тип выводим по шаблону: 761 задача, 186 встреч, 53 напоминания. Падежи чиним (300 — падеж, 8 — «с Стартом» → «со Стартом», 5 — «бюджет по бюджету»), исходник храним в `title_original`. Статус — `unknown`: не выдумываем.

**9. Почему статус `unknown`, а не `open`?**
В данных его нет. Записать `open` у события 2024 года — выдумка; `done` — тоже. `unknown` честно говорит «не знаем» и не мешает ни спискам, ни поиску.

**10. Почему разбор CSV шаблонами, а не LLM?**
Данные шаблонные — регулярки покрывают 100% строк, работают за ~3 с на весь файл, детерминированы и проверяются тестами. LLM на 1000 строк дал бы недетерминизм и стоимость без выигрыша в качестве. Для незнакомого текста есть страховка `_fallback`.

**11. Импорт повторяется на каждом старте — дублей не будет?**
Нет: каждая запись помнит `source_ref = "csv:<id>"`, импорт пропускает уже загруженные, а в базе уникальный индекс `(user_id, source_ref)`. Повторный запуск: `skipped_existing: 1000, inserted: 0`.

**12. Как работает «отмени»?**
Каждое изменение пишется в `actions` со снимками записи до и после. Undo: созданную — мягко удаляем, удалённую — восстанавливаем (`deleted_at = NULL`), изменённую — возвращаем снимок «до». Поэтому удаление мягкое.

**13. Как храните время? Что с часовыми поясами?**
`timestamptz`, в базу пускаем только время с поясом — naive отклоняется ошибкой. Встреча — интервал `starts_at/ends_at`, задача — точка `due_at` и флаг `has_time`. Сравниваем и показываем в Europe/Moscow.

**14. Как ассистент понимает, что «была» — это прошлое?**
NLU ставит `tense = past` по глаголу; поиск фильтрует `sort_at < now` и сортирует «свежие первыми». Если NLU не понял, поиск сам берёт время из слов «старую», «прошедшие», «давнюю». Оракул O3 в каверзных проверяет, что «прошлое» никогда не возвращает будущее.

**15. Как отвечает, если ничего нет?**
Честным «не нашёл». Если совпало только слово-тип («встреча»), а предмет («с дизайнером», «с Петром») нет — пусто, а не «похожие встречи». В эталоне это отдельная метрика — 100%.

*Запасные:* «Зачем два хранилища?» — память для разработки и CI без базы, PostgreSQL для стенда; паритет выдачи проверяет тест (209 тестов слоя данных зелёные). «Почему 1024 измерения?» — размерность `USER-bge-m3`; hash-эмбеддер сделан той же размерности, чтобы переключение не требовало миграции.
